01 / 05

Data + Text-Only Baseline

Get the data flowing and build your first working classifier — text only, no images yet.

~1–2 weeks Python, pandas, scikit-learn, HuggingFace
Steps
  1. Set up your environment. Install Python (3.10+), create a virtual environment, and use Google Colab or Kaggle Notebooks for free GPU access — you don't need a local GPU for this project. Why: fine-tuning BERT later needs a GPU; local CPU training would take hours instead of minutes.
  2. Download the Fakeddit dataset. It comes with text, image links, and labels (2-way, 3-way, 6-way). Start with the 2-way (real/fake) labels. Why: starting with binary classification keeps the problem simple before you add complexity.
  3. Do exploratory data analysis (EDA). Check class balance (`value_counts()`), text length distribution, and how many rows actually have a working image link. Why: if one class has 5x more samples than the other, your model will cheat by always guessing that class unless you handle it.
  4. Clean the text. Lowercase it, strip URLs/HTML tags/extra whitespace. Don't over-clean — keep punctuation and emojis if present, they can be genuine signal for fake news style. Why: fake news often has different "style" (excessive punctuation, clickbait phrasing) — cleaning too aggressively erases that signal.
  5. Build a baseline model first: TF-IDF + Logistic Regression. Use scikit-learn's `TfidfVectorizer` and `LogisticRegression`. This should take under an hour to build. Why: always build the dumbest reasonable model first — it tells you if your data pipeline works, and gives you a number to beat.
  6. Upgrade to a fine-tuned transformer (DistilBERT or BERT). Use HuggingFace's `transformers` library — load a pretrained model, add a classification head, fine-tune on your labeled text. Why: pretrained transformers already "understand" language; you're just teaching the last layer to recognize fake-vs-real patterns.
  7. Split your data properly: train / validation / test. Use `train_test_split` with stratification on the label column. Why: stratifying keeps the same real/fake ratio in every split, so your validation accuracy isn't misleading.
  8. Add your first explainability layer. Use `shap` on the TF-IDF+LogReg model, or extract attention weights from the BERT model, to see which words pushed the prediction toward "fake." Why: this is the whole point of the project — get in the habit of checking *why* early, not bolting it on at the end.
Concepts worth understanding (not just using)
TokenizationSplitting text into words/sub-words the model can process as numbers.
TF-IDFA score that weighs a word by how often it appears in a document vs. how common it is overall — rare-but-frequent words score high.
EmbeddingsTurning a word/sentence into a list of numbers (a vector) that captures its meaning — similar meanings end up as similar vectors.
Transfer learning / fine-tuningTaking a model already trained on huge text data and adjusting it slightly for your specific task, instead of training from scratch.
OverfittingWhen a model memorizes the training data instead of learning general patterns — shows up as high train accuracy, low validation accuracy.
Class imbalanceWhen one label has far more examples than another, which can silently bias your model.
Common beginner pitfalls
  • Splitting train/test after cleaning the whole dataset together — always split first, then process each split separately, to avoid data leakage.
  • Forgetting to move both the model and the data to the GPU (`.to('cuda')`) — training silently runs on CPU and takes forever.
  • Using a different tokenizer/preprocessing at inference time than the one used in training — predictions will be wrong or nonsensical.
  • Judging the model only on overall accuracy when classes are imbalanced — check precision/recall/F1 per class instead.

02 / 05

Image-Only Branch

Build the visual half of the pipeline — a classifier that looks at the image alone, plus a heatmap explaining what it looked at.

~1–1.5 weeks PyTorch, torchvision, Grad-CAM
Steps
  1. Download and inspect the images. Fakeddit gives you image URLs/files — check for broken links, corrupted files, and very small/low-res images before training on them. Why: a few corrupted files can crash a training loop hours in if you don't filter them first.
  2. Preprocess images correctly. Resize to the input size your chosen model expects (e.g. 224×224), and normalize using the same mean/std values the pretrained model was originally trained with. Why: pretrained CNNs expect input in a specific numeric range — get this wrong and the model performs badly for no obvious reason.
  3. Choose a pretrained backbone. Start with ResNet50 (simpler, well-documented) via `torchvision.models`. Try a Vision Transformer (ViT) later for comparison if time allows. Why: ResNet50 is the most beginner-friendly, forgiving architecture to fine-tune — good first choice before anything fancier.
  4. Freeze most layers, fine-tune the last few. Freeze the early convolutional layers (they detect generic edges/textures) and only train the last block + your new classification head. Why: training the whole network from scratch on a small dataset causes severe overfitting; the early layers don't need to change.
  5. Use light data augmentation. Random crops, flips, slight color jitter — via `torchvision.transforms`. Why: augmentation artificially grows your effective dataset size and makes the model less sensitive to irrelevant variations.
  6. Train and evaluate the same way as Module 1 — accuracy, precision/recall/F1, on a held-out test set.
  7. Add Grad-CAM explainability. Use the `pytorch-grad-cam` library to generate a heatmap over the image showing which regions most influenced the "fake" or "real" decision. Why: Grad-CAM is the image-side equivalent of SHAP for text — it's what lets you literally show "the model looked here."
Concepts worth understanding
ConvolutionA CNN scans small patches of the image with filters to detect edges, textures, then shapes, layer by layer.
Pretrained backboneA CNN/ViT already trained on millions of general images (ImageNet) — it already "knows" basic visual features.
Freezing layersLocking certain layers so their weights don't update during training — keeps what they already learned intact.
Data augmentationRandomly modifying training images (crop, flip, color) each epoch so the model sees more variety.
Class Activation Map (Grad-CAM)A heatmap generated from a CNN's internal gradients, showing which pixels most affected the output prediction.
Common beginner pitfalls
  • Using ImageNet's normalization stats with a model that wasn't pretrained on ImageNet — always match the backbone's expected preprocessing.
  • Unfreezing and fine-tuning the entire network on a small dataset — this almost always overfits fast for a beginner project.
  • Not checking for broken/missing images before the training loop starts — filter these out during preprocessing, not mid-training.
  • Generating Grad-CAM from the wrong layer — it needs to target the last convolutional layer, not the final classification layer, to produce a meaningful spatial heatmap.
Tools you'll use
PyTorchtorchvisionPIL / Pillow pytorch-grad-cammatplotlib

03 / 05

Fusion + Cross-Modal Explainability

Combine text and image into one model, then build the explanation that makes this project stand out — why text and image agree or disagree.

~1.5–2 weeks Core differentiator module
Steps
  1. Extract embeddings from both branches. Take the second-to-last layer output from your Module 1 text model and Module 2 image model — this gives you a fixed-length vector representing each. Why: you don't need the final classification layer, just the "understanding" the model built before it — that's what gets fused.
  2. Build late fusion first. Concatenate the text embedding and image embedding into one vector, feed it into a small new classifier (a couple of dense layers). Why: this is the simplest fusion approach to get working end-to-end before adding complexity — get a baseline multimodal number first.
  3. Compare against your unimodal baselines. Multimodal accuracy should beat both text-only and image-only — if it doesn't, something's wrong with the fusion, not the concept.
  4. Upgrade to cross-attention fusion (optional but recommended). Let the text embedding "attend to" the image embedding and vice versa, so the model learns which parts of each modality relate to each other. Why: this produces attention weights you can reuse directly as explainability output — a natural upgrade path, not just extra complexity.
  5. Compute a text-image agreement score. Use cosine similarity between the two embeddings (or the cross-attention weights) as a simple "how much do these two modalities agree" signal.
  6. Build the natural-language explainer. Write a small rule-based function: if the agreement score is low and the image branch's confidence dominates, output something like "Flagged mainly due to a mismatch between the claim and the image." If text dominates, phrase it around wording/style instead. Why: this is your project's unique contribution — most systems explain each modality separately and never explain the fusion decision itself.
Concepts worth understanding
Embedding spaceThe numeric "meaning space" where similar things (in text or images) end up close together as vectors.
Cosine similarityA measure of how aligned two vectors are (1 = identical direction, 0 = unrelated, -1 = opposite) — used to compare text and image embeddings.
Early vs. late fusionEarly fusion combines raw features before much processing; late fusion combines each modality's already-processed output. Late fusion is easier to debug.
Attention mechanismA way for a model to learn "how much weight" to give different pieces of input when making a decision — here, how much to trust text vs. image.
Common beginner pitfalls
  • Training the fusion head while also letting the text/image branches keep updating — freeze them first, get fusion working, then consider fine-tuning end-to-end.
  • Text and image embedding dimensions not matching when concatenating — check `.shape` before feeding into the fusion layer.
  • Overfitting the fusion head on a small number of samples — it's a small model, but still needs enough data and regularization (dropout).
  • Treating a high agreement/disagreement score as proof of truth by itself — it's one signal, not a verdict; keep it paired with the classifier's actual prediction.
Tools you'll use
PyTorchnumpyscikit-learn (cosine_similarity)

04 / 05

Evaluation: Faithfulness + Robustness

Prove your explanations are actually trustworthy — not just pretty pictures. This is the part almost nobody else in this space does properly.

~1 week Your second differentiator
Steps
  1. Run a faithfulness (deletion) test on text. Take the top-k SHAP words for a prediction, mask/remove them, and re-run the model. If confidence drops sharply, the explanation is faithful. Why: a heatmap that looks convincing but doesn't actually affect the model's decision is misleading, not explainable.
  2. Run the same test on images. Blank out or blur the top Grad-CAM region, re-run the model, check the confidence drop.
  3. Plot deletion curves. Remove words/regions in decreasing order of importance and plot how confidence drops as a curve — a steep early drop = good explanation.
  4. Test missing-modality robustness. Run your fusion model with only text (blank/zero image embedding) and only image (blank text embedding). Record how much accuracy drops in each case. Why: real-world posts are often text-only or image-only — this tells you (and anyone reviewing your project) how the model behaves outside ideal conditions.
  5. (Optional) Compare against a large vision-language model. Send the same text+image pairs to an existing VLM (e.g. via an API) and compare its accuracy and explanation style to yours. Why: this shows where your lightweight, explainable approach stands relative to a heavyweight system, without you having to train one.
  6. Build one summary comparison table covering: text-only, image-only, late fusion, cross-attention fusion (and VLM if included) — accuracy, F1, and faithfulness score side by side.
Concepts worth understanding
FaithfulnessWhether an explanation actually reflects what drove the model's decision, as opposed to just looking plausible to a human.
Deletion/insertion metricRemove (or add back) the "important" parts one at a time and track how prediction confidence changes — a quantitative faithfulness check.
Ablation studySystematically removing or disabling one part of a system (e.g. one modality) to measure its individual contribution.
RobustnessHow well a model holds up under conditions it wasn't specifically optimized for, like missing input.
Common beginner pitfalls
  • Only reporting accuracy and skipping faithfulness entirely because it feels optional — it's the part that makes this project different from a generic fusion model.
  • Testing missing-modality behavior by literally removing input shape rather than zeroing/masking it consistently with how the model was trained to expect input.
  • Eyeballing "the numbers look different" instead of reporting the actual delta — always put real numbers in the comparison table, not impressions.
  • Forgetting to test faithfulness on both correct and incorrect predictions — faithfulness matters especially when the model is wrong.
Tools you'll use
pandasmatplotlibshap pytorch-grad-camVLM API (optional)

05 / 05

Demo + Writeup

Package everything into something a stranger — or an interviewer — can actually open, use, and understand in five minutes.

~1 week Streamlit, README
Steps
  1. Save your trained models properly. Use `torch.save(model.state_dict(), ...)` for each branch (text, image, fusion) so they can be reloaded without retraining. Why: retraining every time you restart your notebook wastes hours — checkpoint early and often.
  2. Build a simple inference pipeline function. One function that takes raw text + an image file, runs it through preprocessing → both branches → fusion → explanation, and returns everything needed for display.
  3. Build the Streamlit app. A text box, an image upload widget, a "Predict" button, and an output area showing: label, confidence, highlighted text (color-coded by SHAP importance), the image with Grad-CAM overlay, and the agreement explanation sentence.
  4. Handle missing input gracefully. If the user only provides text or only an image, run the appropriate unimodal branch instead of crashing.
  5. Add a loading state. Inference isn't instant — show a spinner/status message so the app doesn't look frozen.
  6. Write the README/report. Cover: problem statement, architecture diagram, dataset used, results table (from Module 4), example predictions with explanations, and honest limitations (e.g. "trained on Reddit-style posts, may not generalize to other formats"). Why: the writeup is what makes this legible to someone who didn't build it — for a portfolio or interview, it matters as much as the code.
  7. (Optional) Deploy. Streamlit Community Cloud is free and simple if you want a shareable link rather than a local-only demo.
Concepts worth understanding
Model checkpointingSaving a trained model's weights to disk so you can reload and reuse it without retraining.
Inference pipelineThe full sequence of steps from raw input to final output, run at prediction time rather than training time.
Model servingMaking a trained model available to receive input and return predictions through an interface (here, a simple web app).
Common beginner pitfalls
  • Loading a multi-gigabyte model fresh on every single prediction instead of loading it once at app startup — makes the demo painfully slow.
  • Preprocessing input differently in the app than during training (e.g. different image resize or text cleaning) — silently breaks predictions.
  • Skipping the "what this can't do" section in the writeup — naming limitations honestly is what makes a project report credible.
  • Showing raw model output (like class index `0`/`1`) instead of a labeled, human-readable result.
